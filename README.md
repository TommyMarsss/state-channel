# 双方链下状态通道（Go 标准库演示实现）

一个只依赖 **Go 标准库** 与 **原生 HTML/CSS/JavaScript** 的简化双方记账/支付状态通道：
Alice 与 Bob 在链下通过交换"双方签名的状态"更新账本，只有一方不应答或对结算有争议时
才上链仲裁。项目覆盖版本号单调递增校验、链上采信最高版本、争议期欺诈证明与过期处理、
伪造签名识别，并生成一个可逐步回放全部交互的单一静态 HTML 文件。

```
state-channel-a/
├── channel/
│   ├── types.go        # 通道状态、规范化签名载荷、双签状态校验（crypto/ed25519）
│   ├── party.go        # 参与方与链下三阶段更新协议（提案→会签→回送，严格版本递增）
│   ├── chain.go        # 链上仲裁合约：争议、争议期反驳（欺诈证明）、最终结算
│   ├── events.go       # 事件日志与逐步回放所需的只读快照
│   └── channel_test.go # 自动化测试（单调性/仲裁/争议期/伪造签名）
├── web/template.html   # 回放页面模板（原生 JS，零第三方库）
├── main.go             # 驱动 4 组交互场景并把数据内嵌生成 replay.html
└── replay.html         # 运行后生成的单一静态文件（直接双击用浏览器打开）
```

## 运行

```bash
go run .            # 生成 replay.html
go test ./...       # 运行全部测试
go vet ./...
```

生成的 `replay.html` 不启动任何服务、不发起任何网络请求；页面逻辑、样式与全部事件数据
都内嵌在单个文件里。打开后可用按钮、方向键或空格键逐步回放，也可在 `#场景/步`
形式的 URL hash 下定位（如 `replay.html#1/6`）。

## 协议设计

### 1. 状态与双签

每个状态为：

| 字段 | 含义 |
| --- | --- |
| `channelId` | 通道唯一标识，防止跨通道重放 |
| `version` | 状态版本号，必须 **严格单调递增**（从 v1 开始） |
| `balanceA` / `balanceB` | 双方在该版本下的余额 |

签名内容是规范化字节序列（`State.SigningBytes()`），而非 JSON 文本：

```
域分隔前缀 "state-channel/v1/state\n"
  || u16 长度前缀 + channelId（UTF-8 字节）
  || u64be(version)
  || u64be(balanceA)   // 有符号数按补码位模式编码
  || u64be(balanceB)
```

- **域分隔前缀**防止该协议的签名被挪用到其他协议（跨协议重放）；
- 定长大端编码与长度前缀消除字段拼接歧义，保证"签的就是看到的账态"；
- Alice 与 Bob 各用自己的 Ed25519 私钥对同一载荷签名，仲裁只采信 **双签** 状态。
  单签提案只用于链下协商，永远不能上链结算。

### 2. 链下更新协议（三阶段）

1. **提案 Propose**：发起方基于自己已知的最新版本构造 `version = lastVersion + 1`
   的新状态（余额守恒、非负），单独签名后发给对方；
2. **会签 Accept**：应答方依次检查 通道 ID → 余额非负 → 存款守恒 →
   发起方签名有效 → **版本严格新于自己已知版本**，通过后附上自己的签名并立即保存；
3. **回送 DeliverFinal**：完整双签状态返回发起方，发起方用同样的规则校验后保存。
   这一步可能因网络故障/对方离线而丢失——这正是"双方持有不同版本"的来源。

**重放防护**：任何一方"装入"状态时统一走同一入口，先验签名再判
`state.version > lastKnownVersion`。重放旧版本（想撤回对自己不利的更新）、
重复提交当前版本（版本相等而非严格更大）都会以 `ErrStaleVersion` 拒绝。

### 3. 链上仲裁

链下请求超时后，一方可把自己持有的最新双签状态提交给仲裁合约：

- `Dispute`：合约无状态地重新校验 通道归属、余额非负、存款守恒，并
  **分别**核验 Alice/Bob 的 Ed25519 签名；任一签名不匹配即判伪造并拒绝，
  合约保持开启。校验通过则进入长度固定的 **争议期**，记录已采信版本与截止时刻。
- 当双方持有不同版本（如回送消息丢失）时，先上链的可能只是较低版本；
  仲裁规则是"**版本号最高的双签状态获胜**"，不看谁先提交。
- `Settle`：争议期结束后按已采信的最高版本一次性分配双方余额；
  争议期未结束调用返回 `ErrDisputeActive`。

### 4. 争议期与欺诈证明

争议期给诚实的一方一个反驳窗口：

- `Refute` 在 **争议期内（t ≤ deadline）** 提交 `version` 严格更高、双签有效的状态，
  即可使旧版本结算失效、链上改采新版本；提交相等/更低版本返回 `ErrStaleVersion`，
  伪造签名返回 `ErrFinalSig`。
- **超过争议期（t > deadline）后反驳一律拒绝**（`ErrExpiredRefute`），
  旧状态成为最终结算——争议期是刚性的终局边界：没有截止时间，资金永远无法确定归属；
  窗口过短，离线一方又来不及举证。演示中争议期固定为 10 个逻辑时间单位，
  真实系统里该参数应按链的出块时间与对方可接受的最长监控缺席时间来选取。
- 反驳 **不会延长** 争议期（截止时间不后移），避免争议被无限拖延。

### 5. 演示的四组交互（main.go）

| 场景 | 说明 | 预期结果 |
| --- | --- | --- |
| 一 正常更新与重放 | v1→v2→v3 正常转账后，Alice 重放对自己更有利的 v2 | 重放被版本单调性检查拒绝 |
| 二 争议 + 期内反驳 | v3 回送丢失致 A=v2/B=v3 分叉，A 持 v2 上链，B 在 t=9 提交 v3 | v2 结算失效，按 v3（80/20）结算 |
| 三 过期反驳 | 同样分叉，B 在 t=16（截止 t=14）后才提交 v3 | 反驳拒绝，按 v2（90/10）结算 |
| 四 伪造状态 | 攻击者用第三方密钥伪造 v99 中 Bob 的签名上链 | 签名不匹配被拒，合约保持开启，合法 v2 随后正常结算 |

## 自动化测试覆盖

`go test ./channel/` 包含：

- `TestMonotonicUpdatesAndReplay`：正常严格递增更新；重放旧版本、重复提交当前版本、
  旧版本号新签名提案均被拒；透支（负余额）被拒且版本不前进；
- `TestArbitrationHigherVersionWins` / `TestSettleFollowsSubmittedVersionWithoutRefute`：
  双方版本分叉时仲裁采信更高版本；争议期内禁止提前结算；无反驳时按提交版本结算；
  结算后不可再次争议；
- `TestRefuteWithinWindow` / `TestRefuteExpired`：期内反驳成功且争议期不延长、
  低版本反驳被拒；过期后反驳返回 `ErrExpiredRefute` 且旧结算不变；
- `TestForgedStateRejected`：篡改余额、伪造单签、跨通道状态在上链争议与期内反驳
  两条路径上都被正确拒绝；
- `TestEventLogCoversInteractions`：事件序列与逐方签名校验快照可供回放使用。

## 安全边界与简化

这是教学/正确性验证实现，刻意省略了真实支付通道的若干要素：

- 无真实区块链与交易手续费，"链"是进程内对象，时间是共享逻辑时钟；
- 未实现保证金存入/提取交易、单方提款（无合作关通道）、可撤销旧状态的惩罚机制；
- Ed25519 是普通签名而非抗量子的哈希锁/可验证撤销承诺（如 Lightning 的 revocation key）；
- 余额为带符号整数记账单位，没有最小单位/溢出防护之外的资产语义。

协议正确性所依赖的两个不变量与本实现一一对应：**版本号严格递增**（`ingest`/`Accept`）
与 **只有双签且版本最高的状态能在争议期后结算**（`validateState` + `Refute` + `Settle`）。
